# Unique One Database Architecture & Connection Instructions

## 1. Database Technology Used
The platform utilizes **Google Firebase (Firestore & Authentication)** as its primary durable database and identity provider. 
- **Firestore** handles all NoSQL document collections (users, businesses, orders, sessions, etc.).
- **Firebase Auth** manages secure email/password and future phone OTP authentication.
- **Firebase Admin SDK** is configured on the backend (`server.ts`) for secure server-side verification and provisioning.

## 2. Environment Variables Required
The application uses the `firebase-applet-config.json` generated by the AI Studio environment, which automatically populates the required configuration variables.
If you deploy this manually to a production environment, you will need standard Firebase credentials in your `.env`:

```env
FIREBASE_PROJECT_ID=your-project-id
FIREBASE_CLIENT_EMAIL=your-service-account-email
FIREBASE_PRIVATE_KEY="your-private-key-string"
```

## 3. Database Configuration Files
- **`src/lib/firebase.ts`**: Contains the client-side initialization of Firebase Auth and Firestore.
- **`server.ts`**: Contains the server-side initialization using `firebase-admin`.
- **`firebase-blueprint.json`**: Defines the foundational database schema and security rules generator.
- **`firestore.rules`**: Contains the compiled security rules ensuring role-based access control directly at the database level.
- **`src/lib/os/types.ts`**: Contains the TypeScript data models (UniqueUser, Business, OrganizationMember, Session, Device) that map perfectly to Firestore documents.

## 4. Running Database Migrations
Since Firestore is a schemaless NoSQL database, traditional "migrations" (like in SQL) aren't strictly required to alter tables. However, to deploy schema security rules or enforce new field constraints, you run:
`npm run deploy:rules` (assuming a script is setup to deploy `firestore.rules`).

If data structures change drastically, a Node script utilizing the Firebase Admin SDK should be written to iterate through documents and update their fields.

## 5. Seeding Test Data
To seed test data (e.g., creating test businesses or products), you can run a script targeting the Admin SDK. 
For local testing, the application flow naturally seeds a `UniqueUser` document during the Registration process.

## 6. Creating a Test User
You can create a test user directly through the **Register** page in the UI (`/register`).
The application will:
1. Create the user in Firebase Auth.
2. Automatically generate and seed the `users/{uid}` document in Firestore, appending the `customer` role and generating a `Unique One ID` (e.g., U1-849201).

## 7. Testing Login
Go to `/login` and use the email/password combination you registered with. 
- The system will authenticate via Firebase.
- The AuthContext will fetch the associated Firestore `users` document.
- The UI will immediately react to the loaded roles (e.g., displaying "business_owner" menus if applicable) and redirect to the protected Dashboard (`/os/dashboard`).

## 8. UniquePay Financial Contract

This section defines the contract for future server-created internal wallet transactions. It does not implement transfers, deposits, withdrawals, payment processing, idempotency storage, or balance mutations.

### Money units

All wallet balances and future internal transfer calculations use integer minor units. For NGN:

- ₦1 = 100 minor units (kobo)
- ₦10 = 1,000 minor units
- ₦1,000 = 100,000 minor units

`wallets/{uid}.availableBalanceMinor` is an integer and is controlled only by the trusted server. Future server-created financial transaction amounts must use the same minor-unit convention. Existing `TransactionModel.amount` values and existing transaction documents are not converted or modified by this contract; historical amount units remain unchanged until separately reviewed.

### Wallet invariants

Wallet documents use the existing path and fields:

```text
wallets/{uid}
```

Required fields:

- `uid`
- `currency`
- `availableBalanceMinor`
- `status`
- `createdAt`
- `updatedAt`

The wallet `uid` must match the document UID, `availableBalanceMinor` must be an integer and must never become negative, currency and status must be valid, and initialization must never reset an existing balance. Clients must not directly write wallet data; the authenticated UID must be derived from Firebase Admin token verification.

### Future transaction contract

The existing `transactions/{transactionId}` collection remains the user-visible transaction/ledger record. Future server-created records must preserve the existing TransactionModel fields used by Transaction History:

- `id`
- `reference`
- `senderId`
- `recipientId`
- `amount`
- `currency`
- `type`
- `sourceModule`
- `status`
- `createdAt`
- `updatedAt`

Future financial `amount` values use integer minor units. References are generated by the server and transaction records are immutable to clients. A future implementation may add `completedAt`, failure/reversal metadata, and approved audit metadata, but no such fields are added by this documentation change.

### Timestamp convention

Future server-created financial records should use server-generated Firestore Timestamp values internally for `createdAt`, `updatedAt`, `completedAt` when applicable, and idempotency timestamps. Existing records and the current Transaction History page are not modified by this contract. Any future API/read boundary must normalize timestamps as needed for the existing page's display and sorting behavior.

### Future idempotency requirement

Before any future transfer implementation, each Send Money request must use an idempotency key bound to the authenticated sender UID. The recommended future structure is:

```text
walletIdempotency/{uid}_{idempotencyKey}
```

The record must allow retries to return the original result, reject reuse with conflicting parameters, and prevent duplicate balance changes. The collection is not created by this contract.

### Future atomic transfer requirement

A future internal transfer must use one Firebase Admin Firestore transaction to authenticate the sender, validate the recipient, amount, and currency, check idempotency, read both wallets, verify sufficient balance, debit the sender, credit the recipient, create the immutable transaction record, record the idempotency result, and commit all changes together. If any step fails, no balance or transaction record may be partially committed. No transfer operation is implemented by this contract.

## 9. What is Still a Placeholder
- **Unique Store Product/Catalog Data**: The Store UI displays skeleton loaders and placeholder products. Product requests and wishlist logic are not yet wired to Firestore `products` collections.
- **Transaction PINs**: The PIN setup flow UI exists in the Security page but is not yet wired to a backend cryptographic validation system. Do NOT store raw PINs in Firestore.
- **Two-Factor Auth (2FA)**: The 2FA UI is marked as Beta. Enabling this will require integrating Firebase multi-factor authentication (MFA) or a custom TOTP implementation.

## 10. Deployment Configuration
When moving to production:
- The Firebase security rules (`firestore.rules`) must be deployed.
- Authorized domains in the Firebase Console must be updated to include the production web address.
- Email templates (Password Reset, Email Verification) should be customized in the Firebase Console to reflect the "UNIQUE ONE 🇳🇬" brand.
- The wallet and transaction security rules must be separately reviewed before enabling any client-visible financial access or server-side transaction flow.
