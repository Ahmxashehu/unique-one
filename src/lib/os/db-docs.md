# Unique One Database Architecture & Connection Instructions

## 1. Database Technology Used
The platform utilizes **Google Firebase (Firestore & Authentication)** as its primary durable database and identity provider.
- **Firestore** handles all NoSQL document collections (users, businesses, orders, sessions, etc.).
- **Firebase Auth** manages secure email/password and future phone OTP authentication.
- **Firebase Admin SDK** is configured on the backend (`server.ts`) for secure server-side verification and provisioning.

## 2. Environment Variables Required
The application uses the `firebase-applet-config.json` generated by the AI Studio environment, which automatically populates the required configuration variables. If deployed manually, standard Firebase credentials are required in `.env`:

```env
FIREBASE_PROJECT_ID=your-project-id
FIREBASE_CLIENT_EMAIL=your-service-account-email
FIREBASE_PRIVATE_KEY="your-private-key-string"
```

## 3. Database Configuration Files
- **`src/lib/firebase.ts`**: Client-side initialization of Firebase Auth and Firestore.
- **`server.ts`**: Server-side initialization using `firebase-admin`.
- **`firebase-blueprint.json`**: Foundational database schema and security rules generator.
- **`firestore.rules`**: Compiled Firestore security rules.
- **`src/lib/os/types.ts`**: TypeScript data models for the OS domain.

## 4. Running Database Migrations
Since Firestore is a schemaless NoSQL database, traditional SQL migrations are not strictly required. Changes to data structures must be planned explicitly. Existing transaction documents must not be automatically migrated by this documentation step.

## 5. Seeding Test Data
Test data may be seeded through a trusted Admin SDK script. Registration naturally seeds a `UniqueUser` document during the application flow.

## 6. Creating a Test User
A test user can be created through the Register page (`/register`). The application creates the Firebase Auth user and seeds the corresponding `users/{uid}` document.

## 7. Testing Login
Go to `/login` and use the email/password combination used during registration. The AuthContext fetches the associated Firestore user document and redirects authenticated users to the protected dashboard.

## 8. UniquePay Financial Contract
This section defines the contract for future server-created internal wallet transactions. It does not implement transfers, deposits, withdrawals, payment processing, idempotency storage, or balance changes.

### Money units
All wallet balances and future internal transfer calculations use integer minor units. For NGN:

- ₦1 = 100 minor units (kobo)
- ₦10 = 1,000 minor units
- ₦1,000 = 100,000 minor units

`wallets/{uid}.availableBalanceMinor` is an integer controlled only by the trusted server. Future server-created financial transaction amounts must use this same minor-unit convention.

### Wallet invariants
Wallet documents use the existing path and fields:

```text
wallets/{uid}
```

Required fields include `uid`, `currency`, `availableBalanceMinor`, `status`, `createdAt`, and `updatedAt`. The wallet `uid` must match the document UID, `availableBalanceMinor` must be an integer and must never become negative, and initialization must not reset an existing balance.

### Future transaction contract
The existing `transactions/{transactionId}` collection remains the user-visible transaction/ledger record. The existing shared `TransactionModel` is currently retained for compatibility; not every existing transaction document is necessarily a financial record.

Future server-created financial records use the explicit schema documented below. Future financial `amount` values use integer minor units. References are generated by the server and completed financial records are immutable to clients.

## 8.1 UniquePay Financial Transaction Schema

This is the approved schema for every future server-created UniquePay financial transaction. It documents future records only; it does not imply that existing transaction documents already follow this convention.

### Financial record identity

Collection:

```text
transactions/{transactionId}
```

Every future server-created UniquePay financial transaction must contain:

```text
recordKind: "financial"
schemaVersion: 2
amountUnit: "minor"
```

These fields identify the record as a financial record using the approved accounting convention.

### Amount

For NGN, `amount` is an integer number of minor units:

- ₦1 = 100
- ₦10 = 1,000
- ₦1,000 = 100,000

The amount must be an integer safe non-negative integer. Financial accounting must not use floating-point values. Future financial transaction records must not store major-unit values. Conversion to major units occurs only at the presentation boundary.

### Currency

Future UniquePay wallet transfers use:

```text
currency: "NGN"
```

No currency conversion is performed inside the initial wallet-transfer accounting flow.

### Timestamps

Future server-created financial records use Firestore `Timestamp` values internally for:

- `createdAt`
- `updatedAt`
- `completedAt`, when applicable

All financial timestamps are server-generated. At API and UI boundaries, timestamps may be serialized to ISO 8601 strings.

### Existing TransactionModel and future boundaries

The existing shared `TransactionModel` is retained for compatibility. It must not be treated as proof that all existing documents are financial records. Future financial records require the explicit fields:

```text
recordKind: "financial"
schemaVersion: 2
amountUnit: "minor"
```

A future dedicated storage, API, or view-model boundary may be introduced rather than changing the shared model in place.

### Legacy and demo records

- Existing transaction records must not be automatically converted.
- Their amount unit must not be guessed.
- Legacy and demo records must be classified through explicit metadata or provenance.
- Numeric magnitude must never be used to guess whether a value is in major or minor units.
- Unclassified records must not be silently reinterpreted.

### UI and display boundary

The intended boundary is:

```text
Firestore financial record
        ↓
trusted mapper/API serializer
        ↓
UI transaction view model
        ↓
currency formatter
```

For NGN display only:

```text
displayMajorAmount = amountMinor / 100
```

This conversion is presentation-only. It must never be used for wallet balance calculations, transfer validation, ledger calculations, debit/credit calculations, or financial persistence.

### Timestamp normalization

Firestore timestamps should be normalized at the API or mapper boundary into a predictable UI representation, preferably ISO 8601 strings. The UI must not directly assume that every Firestore timestamp is already a string.

### Immutable financial records

After a completed financial transaction is created, clients must not modify:

- transaction ID
- reference
- sender
- recipient
- amount
- currency
- transaction type
- source module
- provider
- timestamps
- financial schema metadata

Corrections must use controlled reversal or adjustment mechanisms rather than editing the original completed transaction.

### Future idempotency requirement

Before any future transfer implementation, each Send Money request must use an idempotency key bound to the authenticated sender UID. A recommended future structure is:

```text
walletIdempotency/{uid}_{idempotencyKey}
```

The collection is not created by this contract.

### Future atomic transfer requirement

A future internal transfer must use one Firebase Admin Firestore transaction to authenticate the sender, validate the recipient, amount, and currency, check idempotency, read both wallets, verify the balance, and apply the corresponding debit and credit atomically.

## 9. What is Still a Placeholder
- **Unique Store Product/Catalog Data**: Product requests and wishlist logic are not yet wired to Firestore product collections.
- **Transaction PINs**: The PIN setup UI is not yet wired to backend cryptographic validation. Raw PINs must not be stored in Firestore.
- **Two-Factor Auth (2FA)**: The 2FA UI is marked as Beta and still requires a production MFA or TOTP implementation.

## 10. Deployment Configuration
When moving to production:
- The Firebase security rules must be deployed.
- Authorized domains must be updated in the Firebase Console.
- Email templates should be customized for the UNIQUE ONE brand.
- Wallet and transaction security rules must be separately reviewed before enabling client-visible financial access or server-side transaction flow.
