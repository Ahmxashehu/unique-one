# Unique One Database Architecture & Connection Instructions

## 1. Database Technology Used
The platform utilizes **Google Firebase (Firestore & Authentication)** as its primary durable database and identity provider.
- **Firestore** handles all NoSQL document collections (users, businesses, orders, sessions, etc.).
- **Firebase Auth** manages secure email/password and future phone OTP authentication.
- **Firebase Admin SDK** is configured on the backend (`server.ts`) for secure server-side verification and provisioning.

## 2. Environment Variables Required
The application uses the `firebase-applet-config.json` generated by the AI Studio environment, which automatically populates the required configuration variables. If deployed manually, standard Firebase Admin SDK environment variables are required:

```env
FIREBASE_PROJECT_ID=your-project-id
FIREBASE_CLIENT_EMAIL=your-service-account-email
FIREBASE_PRIVATE_KEY="your-private-key-string"
```

## 3. Database Configuration Files
- **`src/lib/firebase.ts`**: Client-side initialization of Firebase Auth and Firestore.
- **`server.ts`**: Server-side initialization using `firebase-admin`.
- **`firebase-blueprint.json`**: Foundational database schema and security rules generator.
- **`firestore.rules`**: Compiled Firestore security rules.
- **`src/lib/os/types.ts`**: TypeScript data models for the OS domain.

## 4. Running Database Migrations
Since Firestore is a schemaless NoSQL database, traditional SQL migrations are not strictly required. Changes to data structures must be planned explicitly. Existing transaction documents must not be automatically converted or reinterpreted.

## 5. Seeding Test Data
Test data may be seeded through a trusted Admin SDK script. Registration naturally seeds a `UniqueUser` document during the application flow.

## 6. Creating a Test User
A test user can be created through the Register page (`/register`). The application creates the Firebase Auth user and seeds the corresponding `users/{uid}` document.

## 7. Testing Login
Go to `/login` and use the email/password combination used during registration. The AuthContext fetches the associated Firestore user document and redirects authenticated users to the protected dashboard.

## 8. UniquePay Financial Contract
This section defines the server-created internal wallet transaction contract and current implementation baseline for UniquePay transfers.

### Money units
All wallet balances and internal transfer calculations use integer minor units. For NGN:

- ₦1 = 100 minor units (kobo)
- ₦10 = 1,000 minor units
- ₦1,000 = 100,000 minor units

`wallets/{uid}.availableBalanceMinor` is an integer controlled only by the trusted server. Server-created financial transaction amounts use this same minor-unit convention.

### Wallet invariants
Wallet documents use the existing path and fields:

```text
wallets/{uid}
```

Required fields include `uid`, `currency`, `availableBalanceMinor`, `status`, `createdAt`, and `updatedAt`. The wallet `uid` must match the document UID, `availableBalanceMinor` must be an integer, and currency must be explicitly validated.

### Financial transaction contract
The existing `transactions/{transactionId}` collection remains the user-visible transaction/ledger record. The existing shared `TransactionModel` is retained for compatibility; not every existing transaction document is necessarily a financial record. Server-created financial records use the explicit schema documented below. Financial `amount` values use integer minor units. References are generated by the server and completed financial records are immutable.

## 8.1 UniquePay Financial Transaction Schema

This is the approved schema for every future server-created UniquePay financial transaction. It documents future records only; it does not imply that existing transaction documents already follow this schema.

### Financial record identity

Collection:

```text
transactions/{transactionId}
```

Every future server-created UniquePay financial transaction must contain:

```text
recordKind: "financial"
schemaVersion: 2
amountUnit: "minor"
```

These fields identify the record as a financial record using the approved accounting convention.

### Amount

For NGN, `amount` is an integer number of minor units:

- ₦1 = 100
- ₦10 = 1,000
- ₦1,000 = 100,000

The amount must be an integer safe non-negative integer. Financial accounting must not use floating-point values. Future financial transaction records must not store major-unit values. Conversion between display major units and minor units is presentation-only and must never be inferred from numeric magnitude.

### Currency

Future UniquePay wallet transfers use:

```text
currency: "NGN"
```

No currency conversion is performed inside the initial wallet-transfer accounting flow.

### Timestamps

Future server-created financial records use Firestore `Timestamp` values internally for `createdAt`, `updatedAt`, and `completedAt` when applicable. All financial timestamps are server-generated. At API and UI boundaries, timestamps may be serialized to ISO 8601 strings.

### Existing TransactionModel and future boundaries

The existing shared `TransactionModel` is retained for compatibility. It must not be treated as proof that all existing documents are financial records. Future financial records require the explicit metadata below:

```text
recordKind: "financial"
schemaVersion: 2
amountUnit: "minor"
```

A future dedicated storage, API, or view-model boundary may be introduced rather than changing the shared model in place.

### Legacy and demo records

- Existing transaction records must not be automatically converted.
- Their amount unit must not be guessed.
- Legacy and demo records must be classified through explicit metadata or provenance.
- Numeric magnitude must never be used to guess whether a value is in major or minor units.
- Unclassified records must not be silently reinterpreted.

### UI and display boundary

The intended boundary is:

```text
Firestore financial record
        ↓
trusted mapper/API serializer
        ↓
UI transaction view model
        ↓
currency formatter
```

For NGN display only:

```text
displayMajorAmount = amountMinor / 100
```

This conversion is presentation-only. It must never be used for wallet balance calculations, transfer validation, ledger calculations, debit/credit calculations, or financial persistence.

### Timestamp normalization

Firestore timestamps should be normalized at the API or mapper boundary into a predictable UI representation, preferably ISO 8601 strings. The UI must not directly assume that every Firestore timestamp has the same serialized shape.

### Immutable financial records

After a completed financial transaction is created, clients must not modify its transaction ID, reference, sender, recipient, amount, currency, transaction type, source module, provider, timestamps, or financial schema metadata. Corrections must use controlled reversal or adjustment mechanisms rather than editing the original completed transaction.

### Future idempotency requirement

Each Send Money request uses an idempotency key bound to the authenticated sender UID with this structure:

```text
walletIdempotency/{uid}_{idempotencyKey}
```

The transfer implementation creates and updates this collection server-side.

### Atomic transfer requirement

Internal transfer execution uses one Firebase Admin Firestore transaction to validate request semantics, check idempotency state, read both wallets, verify balances, create financial records, update both wallets, write double-entry ledger rows, and persist the idempotency result atomically. No client-controlled financial fields determine authoritative identity, balances, transaction IDs, references, timestamps, or final status.

## UniquePay Internal Wallet Transfer Contract

**This contract is implemented for internal wallet transfer execution in the server-authoritative flow. It does not imply external payment rail integration or live-money settlement guarantees.**

### 1. Recipient identifier

For the initial internal wallet transfer implementation:

- The recipient is identified by Firebase Auth UID.
- The sender UID **MUST** come from the verified Firebase ID token.
- The recipient UID must be supplied through the server transfer contract.
- Do not use phone number, email, Unique One ID, UniquePay ID, or generated account number for transfer lookup yet.
- Those identifiers may be supported later through an explicit server-side identity-resolution layer.
- Do not infer recipient identity from UI text.

Firebase UID is currently the safest internal identifier because `UniqueUser.uid` exists, Firebase Auth is already the identity provider, Firestore user records are keyed by UID, and no reliable wallet-transfer lookup exists for the other identifiers.

### 2. Wallet existence

Both sender and recipient wallets **MUST** already exist before a transfer can execute. Transfer execution **MUST NOT** silently create wallets. Wallet creation/onboarding is a separate operation, and a missing wallet must result in a stable server-side error. Wallet creation must not be combined with financial transfer execution. This keeps wallet creation separate from financial movement and reduces hidden state transitions and race conditions.

### 3. Wallet status

Initial policy:

- `active` -> transfer allowed
- `suspended` -> transfer rejected
- `locked` -> transfer rejected

The transfer implementation must validate both wallets before changing balances. If the current `WalletDocument` type does not yet contain a formal status enum, implementation must introduce and validate an explicit wallet status contract rather than relying on loose strings.

### 4. Transfer amount

All internal financial amounts **MUST** use integer NGN minor units.

- ₦1 = 100
- ₦10 = 1,000
- ₦1,000 = 100,000

`amountMinor` must be an integer, greater than zero, and used without floating-point accounting. No major-unit amount may be supplied to the financial execution layer. Currency must be `NGN`. Do not use numeric magnitude to guess whether a value is major or minor units.

### 5. Self-transfer

Reject transfers where `senderUid === recipientUid`.

Stable error: `SELF_TRANSFER_NOT_ALLOWED`

A wallet-to-itself transfer creates no economic movement and can pollute financial transaction history and accounting records.

### 6. Transfer limits

Transfer limits are **NOT currently defined**. Do not invent numeric limits. Future production policy must separately define per-transaction limits, daily cumulative limits, velocity/frequency limits, account/wallet restrictions, and possible enhanced verification thresholds. Until explicitly defined, the transfer contract must not silently invent limits.

### 7. Idempotency

Every transfer request requires an idempotency key.

Proposed storage:

```text
walletIdempotency/{senderUid}_{idempotencyKey}
```

Required behavior:

- Same key + identical request: return the original transfer result and do not execute another transfer.
- Same key + different request: reject with `IDEMPOTENCY_KEY_CONFLICT`.
- Concurrent duplicate requests: only one financial transfer may execute; duplicates must resolve to the same committed result or an appropriate deterministic in-progress/final result. Never double-debit or double-credit.
- Same key after successful transfer: return the original completed result and never execute again.
- Validation failures before the transfer transaction begins should not consume the idempotency key.
- Once a financial transfer attempt has entered the atomic execution path and has a recorded final failed result, retain the idempotency key/result so retries return the same outcome instead of unpredictably retrying financial movement.

### 8. Self-contained atomic execution

The financial transfer must eventually execute as one server-side atomic operation. Sender balance update, recipient balance update, transaction creation, and idempotency result creation must not occur outside that atomic operation.

The intended sequence is:

1. Authenticate request.
2. Verify Firebase ID token.
3. Derive sender UID from verified token.
4. Validate request.
5. Validate recipient UID.
6. Reject self-transfer.
7. Validate idempotency key.
8. Resolve sender wallet.
9. Resolve recipient wallet.
10. Require both wallets to exist.
11. Validate both wallets.
12. Validate currency.
13. Validate amount.
14. Check sender available balance.
15. Calculate debit and credit.
16. Create server-generated transaction record.
17. Update sender wallet.
18. Update recipient wallet.
19. Persist idempotency result.
20. Commit atomically.

No client-controlled financial fields may determine the authoritative sender, balance, transaction ID, reference, timestamps, or final financial status.

### 9. Transaction reference

The repository currently contains `TransactionModel.reference`, `ReceiptModel.transactionRef`, and `LedgerEntry.reference`, but there is no finalized financial reference format. The initial rule is:

- Reference is server-generated.
- Reference must be unique.
- Reference must be immutable.
- Client must not provide the authoritative reference.
- The exact production reference format remains an implementation detail to be finalized before the transfer endpoint is released.

Do not create a migration for existing references.

### 10. Transaction status

The initial internal wallet transfer uses a synchronous financial execution model. Initial final states are `completed` and `failed`.

The existing `TransactionStatus` enum may continue to support `pending`, `completed`, `failed`, `reversed`, and `disputed`, but the first internal wallet transfer does not need true asynchronous pending execution. A future pending model would require a durable transaction state machine, worker/queue, retry handling, reconciliation, timeout handling, and provider callbacks/webhooks where applicable.

### 12. Security boundary

Client applications request transfers but must never directly mutate wallet balances or directly create authoritative financial transaction records. Firebase security rules must deny client financial writes. Server-side code using Firebase Admin SDK is responsible for authoritative financial mutation. Sender identity, recipient identity, financial amounts, idempotency, wallet status, sufficient balance, and atomicity must all be validated or enforced server-side.

### 13. Legacy transaction compatibility

Do not reinterpret legacy transactions. Existing transaction records must not automatically be converted into the new financial schema. Future authoritative financial transaction records must explicitly contain:

```text
recordKind: "financial"
schemaVersion: 2
amountUnit: "minor"
```

Do not infer units from numeric magnitude. Do not migrate existing Firestore data.

### 14. Package manager / CI

Repository package-manager facts relevant to this contract:

- `package-lock.json` exists.
- `bun.lock` exists.
- `yarn.lock` does not exist.
- `package.json` is npm-oriented.
- Current CI uses `npm ci`.
- npm remains the current CI package manager.

Do not modify lockfiles.

### 15. Important implementation boundary

These decisions define the contract for the first internal wallet transfer implementation. They do not authorize financial execution. The next implementation step must separately implement and test the transfer endpoint against this contract.

## 9. What is Still a Placeholder
- **Unique Store Product/Catalog Data**: Product requests and wishlist logic are not yet wired to Firestore product collections.
- **Transaction PINs**: The PIN setup UI is not yet wired to backend cryptographic validation. Raw PINs must not be stored in Firestore.
- **Two-Factor Auth (2FA)**: The 2FA UI is marked as Beta and still requires a production MFA or TOTP implementation.

## 10. Deployment Configuration
When moving to production:
- The Firebase security rules must be deployed.
- Authorized domains must be updated in the Firebase Console.
- Email templates should be customized for the UNIQUE ONE brand.
- Wallet and transaction security rules must be separately reviewed before enabling client-visible financial access or server-side transaction flow.
